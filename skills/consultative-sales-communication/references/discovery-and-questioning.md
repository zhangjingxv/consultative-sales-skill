# 需求发现与提问

## 目标

帮助客户和销售共同判断问题是否真实、是否值得解决、需要哪些角色和证据。不要把提问变成审讯或完整表单。

## 最小发现链

1. **结果**：客户希望发生什么变化？
2. **现状**：现在如何处理，哪里不满足？
3. **影响**：不改变会影响什么人、指标、时间或风险？
4. **约束**：技术、预算、时间、流程和政策中什么不能动？
5. **标准**：客户会用什么证据判断方案有效？
6. **路径**：谁使用、谁评估、谁决定、谁采购、谁验收？

按当前最可能改变方向的一项提问，不要机械走完六步。

## 问题类型

- **事实问题**：确认数量、节点、角色、环境和现状。
- **分叉问题**：确认哪个条件最影响方案，例如性能、容量还是交期。
- **影响问题**：确认问题的重要性，不诱导客户夸大痛苦。
- **标准问题**：确认验收和决策标准。
- **承诺问题**：确认下一动作、责任人与时间。

## 降低审讯感

- 先说明为什么这个问题会改变方案。
- 一次只问一个主要问题。
- 客户回答后先复述确认，再问下一层。
- 在对话中适量加入有用判断，不让客户持续“填表”。
- 问不到时保持未知，不替客户补答案。

## 可用结构

```text
为了不把方案做偏，我先确认一个最关键的点：【问题】？
```

```text
我听下来，您最先要解决的是【已确认结果】，当前主要受【已确认约束】影响。我理解得对吗？
```

```text
如果只能先改善一项，您更看重【A】还是【B】？这会决定我们下一步先验证什么。
```

## 失败模式

- 一条消息连续询问场景、预算、时间、人数、权限和竞品。
- 为了制造紧迫感而夸大损失。
- 只问产品参数，不理解客户要改变的业务结果。
- 客户尚未确认问题，就急着讲完整解决方案。
- 把“预算多少”当作发现需求的第一句话。
